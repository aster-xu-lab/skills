# 边界拆分与复用判据

本文件回答两个问题：这段代码该不该拆；这段重复该不该抽取。

## 一、边界拆分

### 1. 删除测试

设想删掉这个模块或这层抽象：

- 复杂度随之消失：它只是转发或包装，属于浅模块，考虑内联。
- 复杂度转移到 N 个调用方：它承载了真实知识，应当保留；若接口仍很宽，考虑加深接口。
- 复杂度原地不动：它可能是纯粹的分层形式，需要重新确认职责。

### 2. 变化率与变更原因

- 因不同原因变更是拆分线索；先确认拆分能减少联动，再决定，不仅因当前同时包含 I/O 与计算就拆。
- 总是同时变更、且变更原因相同的代码，可以合并。
- 变更频率差异大时，优先按变更原因拆，而不是按文件行数拆。

### 3. 依赖方向

- 区分运行时调用方向与源码依赖方向，按项目分层或端口与适配器约定判断。
- 底层依赖上层具体实现是审查线索；通过约定的抽象契约回调不直接认定为反向依赖缺陷。
- 跨层直连（例如展示层直接调用数据层）应通过约定的接缝收敛。

### 4. 状态所有权

- 同一业务状态明确权威写入者；读模型、缓存或渲染副本可以存在，但须有同步、失效与版本规则。
- 其他方通过接口读取或提交变更，不直接改写。
- 出现多个可写入口时，先确定真源，再迁移写路径。

### 5. 接缝与可测试性

- 好的接缝能让人在不启动完整运行时的情况下测试核心逻辑。
- 以可观察行为作为测试面；核心行为只能绕过外部接口测试时检查接缝。内部接缝可支持模块自己的测试，不因其存在就判定设计错误。
- 为了测试而暴露内部状态，通常是边界没切好的信号。

### 6. 接口宽度与模块深度

- 深模块：小接口，隐藏大量实现。
- 浅模块：接口和实现一样复杂，调用方仍需理解内部细节。
- 加深的方向通常是：合并零散参数为有意义的输入、隐藏实现细节、把变化收敛到模块内部。
- 接口不仅是方法签名，还包含调用者必须知道的不变量、顺序、错误、配置与性能要求。把参数塞进一个对象而不减少这些知识，不算加深。
- 比较重构前后需要理解的概念与跨文件跳转是否减少；减少行数或新建更多小模块本身不构成收益。

## 二、复用判断

### 1. 三次规则

三次规则是避免过早抽象的启发式，不是次数门禁。两处已经共享稳定规则且必须同步修复时也可抽取；出现三次但语义不同仍不合并。

### 2. 知识重复与形状重复

- 知识重复：语义相同，未来也会一起变化，应该抽取。
- 形状重复：代码长得像，但业务含义不同，未来会分别演化，不应抽取。
- 判断方法：问“如果一边的需求变了，另一边是否必须跟着变”。答案是否，就不要合并。

### 3. 抽象顺序

优先抽取：

1. 纯函数与纯数据类型。
2. 稳定的契约或接口。
3. 最后才考虑基类、高阶组件、通用框架。

这个顺序仅作为起点；实际比较调用方需要承担的知识与迁移成本，不把纯函数或接口本身当作收益。

### 4. 先查已有能力

抽取前先确认项目或依赖中是否已有：

- 相同语义的类型或工具函数。
- 已存在的共享层或契约层。
- 标准库或框架提供的等价能力。

重复实现已有能力，比重复代码本身更值得处理。

### 5. 复用的边界

- 不为“可能的未来复用”提前抽象。
- 不为消除少量重复而引入跨模块依赖。
- 抽象后若只有一个调用方，且没有收敛变化，考虑回退为内联。

## 三、重构候选的输出

每个候选至少写清：

| 字段 | 内容 |
| --- | --- |
| 现状 | 当前职责、依赖和问题 |
| 目标结构 | 拆分或合并后的边界 |
| 收益 | 可验证的改善：可测试性、变更局部性、重复消除 |
| 风险 | 行为变化可能性、影响面、回滚难度 |
| 影响面 | 调用方、测试、构建与发布链路 |
| 验证方式 | 用哪套命令或路径确认行为不变 |

没有证据支撑的收益不写；无法验证的候选标为“待确认”。
