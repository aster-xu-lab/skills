# 变更日志与契约文档

变更日志写给**使用者**，契约文档写给**集成方**。两者都以“对方需要知道什么”组织，不以实现过程组织。

## 变更日志

### 面向谁

- 使用该服务、SDK、桌面应用或 API 的人。
- 需要判断“要不要升级、升级会不会坏”的人。

不写给内部提交者；提交历史不是变更日志。

### 结构

```markdown
# Changelog

## [版本] - YYYY-MM-DD

### 新增
- 用户可感知的新能力。

### 变更
- 行为、配置、默认值的变化；说明影响。

### 修复
- 修复的问题与影响范围。

### 弃用
- 将移除的能力、替代方案、移除时间。

### 移除
- 已移除的能力与迁移方式。

### 安全
- 安全修复；不暴露可利用细节。
```

### 规则

1. **按使用者影响分类**，不按提交类型机械罗列。
2. **写影响与迁移方式**：不只写“升级了依赖”。
3. **版本与日期来自发布事实**，不提前写未发布内容。
4. **破坏性变更单独突出**：旧行为、新行为、迁移步骤。
5. **不写内部工单号作为唯一说明**；外部读者看不懂。
6. **修复安全问题时**说明受影响版本与升级建议，不写攻击细节。

## 契约文档

### 覆盖什么

- HTTP/RPC 端点、方法、路径、鉴权。
- 请求/响应字段：类型、必填、默认值、枚举、格式。
- 错误码、错误体结构、HTTP 状态。
- 幂等语义、重试建议、超时。
- 事件/消息的字段、顺序、重复与兼容性。
- 配置项：键、类型、默认值、生效范围。

### 规则

1. **以 schema 或代码为真值**：文档与 schema 不一致时，先修 schema 或说明差异，不手写第二套事实。
2. **字段表穷尽**：每个字段有类型、必填、默认值、说明；参考性文档不省略。
3. **错误可机读**：稳定错误码 + 人类可读说明；不只给一段自然语言。
4. **兼容性写清**：新增字段是否可选、旧客户端如何表现、弃用时间线。
5. **示例最小且真实**：示例能直接对照 schema；不写含真实密钥的示例。
6. **不复制实现细节**：契约描述外部可见行为，不描述内部类结构。
7. **版本化**：契约变更与 API 版本策略一致；破坏性变更走新版本或迁移窗口。

## 反模式

- 变更日志从提交记录直接生成，使用者看不懂。
- 只写“优化了性能”，不写影响与验证方式。
- 契约文档漏字段、漏默认值、漏错误码。
- 文档与 schema 各写一套，互相矛盾。
- 示例使用真实 token、内网地址或个人信息。
- 破坏性变更不标迁移步骤。
- 把内部实现重构写成对外变更。
