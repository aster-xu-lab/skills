# ADR 与决策日志

一个决定要么进 ADR，要么进决策日志。**已接受的记录只追加，不改写。**

## 先探测项目约定

写之前检查：

- 是否已有 `docs/adr/`、`docs/decisions/`、`.adr-dir` 或类似位置。
- 现有编号、文件名、扩展名、章节标题与语言。
- 是否有模板或工具（adr-tools、MADR 等）。

项目已有约定时，沿用它；没有时才用本文默认格式。不要另起第二套编号。

## 选 ADR 还是决策日志

| 形式 | 适合 | 不适合 |
| --- | --- | --- |
| ADR | 架构级、难回退、跨团队、需要长期引用 | 日常小选择 |
| 决策日志 | 运行中的小决定、快速留痕 | 需要完整论证的重大决策 |

拿不准时：**难回退就写 ADR，否则写日志。**

## ADR 骨架

```markdown
# ADR-<编号>：<决定的短标题>

| 项 | 内容 |
| --- | --- |
| 状态 | 提议中 / 已接受 / 被 ADR-XXX 取代 / 已废弃 |
| 日期 | YYYY-MM-DD |
| 决策者 | 参与决定的人或角色 |

## 上下文
技术、组织、约束等作用力；要解决什么。只陈述事实，不提前给结论。

## 决策
决定了什么。用主动语态：“我们在标签上发布”，不写“据决定……”。

## 后果
**正面：** 什么变容易。
**负面：** 什么变难、接受了什么代价。**不可为空。**
**中性：** 什么变了但不好不坏。

## 考虑过的替代方案
**<替代方案>** — 支持理由：……；反对理由：……；为什么没选：……

## 参考
证据、相关决策、测量结果。
```

## 决策日志骨架

```markdown
## YYYY-MM-DD

### <用祈使句陈述决定>
一段说明规则。

为什么：
- <理由>
- <理由>

而不是：<被否方案> — <为什么没选>
```

## 规则

1. **追加式**：已接受的记录不改写；新情况写新条目并注明取代关系。纠错用带日期的新条目。
2. **负后果必填**：只写好处不是决策记录，是宣传。
3. **替代方案写最强论点**：不写就是稻草人。
4. **记录 why，不只 what**：代码能说明做了什么，记录要说明为什么。
5. **相对日期转绝对**：写 `2026-11-28`，不写“上周”。
6. **决定前先记录**：聊天、PR 评论不是耐久来源；把实质写进日志，再引用。
7. **最小完整决定**：不是聊天记录，不是会议纪要。
8. **范围声明**：同主题有兄弟文档时，在顶部写清本文负责什么、什么留给别的文档。

## 常见触发信号

出现这些话时，通常有未记录的决定：

- “我们决定用 X 而不是 Y。”
- “就这么定了吧。”
- “这个取舍我们在 PR 评论里讨论过。”
- 同一个人第二次解释同一个理由。

此时提议记录，不擅自替人拍板。

## 反模式

- 改写已接受的 ADR，掩盖历史变化。
- 负后果留空，或只写“有一定学习成本”。
- 替代方案只写缺点。
- 一个 ADR 塞多个决定。
- 决策只存在于聊天或 PR 评论。
- 新建第二套编号，与现有 ADR 冲突。
- 把提议写成已接受。
