# 事故复盘与 runbook

复盘写给**一年后遇到类似问题的人**，不是写给当时在场的人。runbook 写给**需要照着执行的人**，每一步都必须真实跑过。

## 事故复盘

### 何时写

- 事故已恢复，或长事故到达稳定里程碑。
- 到达用户的缺陷、数据问题、near miss（差点出事但被拦住）同样写。
- 事故进行中不写复盘，用 runbook 处置。

不用于：追责、对外状态通报。

### 骨架

```markdown
# <系统>：<一句话描述故障症状>

| 项 | 内容 |
| --- | --- |
| 事故日期 | YYYY-MM-DD |
| 持续时间 | 从发现到恢复 |
| 严重度 | 按组织定义；没有定义就写“未定义”，不编 |
| 状态 | 草稿 / 已评审 |

## 摘要
用户可见影响（带数字）、根因一句话、当前状态。只看这一段也能知道发生了什么。

## 影响
谁、什么、多少：失败请求、受影响记录、金额或时间。估算要标“估算”；写“未发现数据丢失”前必须说明检查了什么。

## 时间线
按时间戳列事实，每条可追溯到告警、日志、提交或消息。解释放在下面章节，不放在时间线。

## 根因与贡献因素
机制，落到代码与提交。贡献因素列清单；“每个组件都正确，缺陷在组件之间”也是有效根因。写清哪一层检查漏了、哪一层拦住了。

## 处置中的错误转向
第一个错误修复、跟错的信号、浪费一小时的假设。这些是内容，不是羞耻。

## 行动项
每项有负责人、验收方式，关联到任务系统。“后续调查 X”没有负责人不算行动项。

## 签署
- YYYY-MM-DD <评审人>：通过 <范围>
```

### 规则

1. **无责是结构性的**：写角色、门禁、依赖、缺失的防护，不写人名。归咎个人只会得到“下次小心”。
2. **时间线是证据**：时间戳来自系统，不凭记忆；只有记忆来源时明确标注。
3. **错误修复要写**：当时合理但没用的修复，连同它为什么看起来合理。
4. **严重度用组织定义**：没有定义就留空，不发明。
5. **行动项可执行**：结果、负责人、验收、已建单并链接；不能建单时标 `[待建单：谁]`，复盘保持草稿直到链接存在。
6. **评审后不可改写**：新发现用带日期的追加；重写复盘等于伪造记录。
7. **near miss 用同一骨架**：影响写“如果发生会怎样”，标明是反事实。
8. **后续决定另记**：复盘引出的新规则或策略，用 ADR/决策日志记录并链接，不塞进复盘正文。

## runbook

### 何时写

- 发布、回滚、迁移、排障、故障处置等需要重复执行的步骤。
- 事故暴露了缺失或过时的操作步骤。

### 骨架

```markdown
# Runbook：<操作名>

| 项 | 内容 |
| --- | --- |
| 适用场景 | 什么时候用、什么时候不用 |
| 前置条件 | 权限、环境、工具、备份 |
| 影响范围 | 会改什么、谁受影响 |
| 维护者 | 角色或团队 |

## 步骤

### 1. <动作>
命令：
预期输出：
失败时：<现象、处理、何时停止>
验证：<如何确认这一步成功>

### 2. ...

## 回滚
逐步回退方式；哪些步骤不可逆。

## 验证
完成后的检查项与成功判据。

## 变更记录
- YYYY-MM-DD：<改了什么、为什么>
```

### 规则

1. **每一步真实跑过**：没跑过的步骤标 `[未验证]`，不写成确定可执行。
2. **写清前提**：权限、环境、版本、备份；缺前提时停下。
3. **命令可复制**：占位符用 `<...>`，不写真实密钥。
4. **每步有验证**：怎么知道成功；不靠“看起来没报错”。
5. **失败路径**：常见失败、何时停止、如何回滚。
6. **不可逆步骤单独标注**：删除、覆盖、切流量前要求确认。
7. **随现实更新**：runbook 与实际不符时更新，并记录变更。

## 反模式

- 复盘写成追责名单。
- 时间线混入推测和情绪。
- 行动项没有负责人和验收。
- 复盘评审后还在改写。
- runbook 步骤从未执行，或命令里有真实密钥。
- runbook 没有回滚和失败处理。
- 把“加强意识”“注意检查”当成行动项。
