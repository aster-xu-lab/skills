# 审查轴与判据

本文件只补充 `commit-history-review` 的检查细节。项目约定、用户授权和实际证据优先于本文。

## 输出纪律

- 每条发现给“提交 + `文件:行` + 证据”；证据不足放“待确认”，不混入结论。
- 区分硬违规（项目文档明确要求）与判断项（通用启发式）；判断项标注“可能/建议”。
- 已被格式化器、linter、类型检查、构建门禁覆盖的项不重复报告。
- 格式化、lint、类型检查等工具类结论必须先归因到被审提交：在基线（父提交或范围起点）上运行同一检查。基线同样失败的不列为本次发现，必要时只写“既有漂移，非本提交引入”。可用 `git show <base>:<path>` 与 `git show <head>:<path>` 分别运行同一检查；工具依赖文件路径解析配置时，使用其 stdin 路径参数或临时检出保留原路径。不要假设配置文件扩展名；配置不可解析或基线无法运行时标“待确认”，不强行归因。
- 先写清“改了什么、为什么改”，再判断“是否做对”；不要用提交信息替代对 diff 的阅读。

## A 正确性与风险

按影响排序，优先看：

- 逻辑错误、边界条件、空值、差一错误、状态不一致。
- 并发竞态、可见性、锁范围、异步取消与恢复。
- 事务边界、自调用失效、异常类型不回滚、跨远程调用的事务。
- 资源泄漏：连接、流、文件句柄、线程池、监听器。
- 幂等、重复提交、部分失败与重试语义。
- 输入校验、鉴权、越权、数据隔离、日志泄漏敏感信息。
- 历史提交中新增或改动的密钥、令牌、内网地址；发现时只报告位置与处置建议，不复述完整值。

Java/Spring 的专项检查交给目标项目或已安装的专用 Java 审查能力，本文件不重复。

## B 契约与意图

- 提交声称做了什么？diff 实际做了什么？两者是否一致。
- 是否夹带未声明的重构、格式化、依赖升级或无关文件。
- 公共 API、RPC、事件、DTO、数据库 schema、配置键是否兼容；旧数据与旧客户端是否受影响。
- 调用方、迁移脚本、测试、文档是否同步补齐。
- 仓库若维护 Agent 规则、领域 Skill 或命令资产（如 `AGENTS.md`、`CLAUDE.md`、`.agents/skills/**`、`.claude/**`），行为或流程规则变更是否同步；没有这类资产时不强行检查。领域规则是后续会话的入口，过期比缺失更易误导。
- 提交信息与实际改动是否匹配；混合关注点是否应该拆分。
- 没有需求文档时，按提交意图和用户可见行为判断，不虚构 spec。

## C 质量与一致性

- 命名是否表达意图；是否有误导性名称或缩写。
- 重复逻辑是否只是形状相似，还是共享同一业务知识；不要因相似就强行合并。
- 分层与依赖方向是否符合项目既有结构；新逻辑是否漏进共享模块。
- 抽象是否过度；是否为未出现的需求预留参数或钩子。
- 错误处理是否吞异常、把失败转成成功、丢失上下文。
- 测试是否真正能失败；是否只断言 mock 调用而没有行为验证。

不采用固定行数、嵌套深度或“函数必须小于 N 行”的机械阈值；项目约定优先。

## D 提交卫生

轻量检查，不喧宾夺主：

- 提交是否原子；是否把无关改动混在一起。
- 提交信息是否准确描述效果，而不是只写“修改”“优化”。
- 提交附带的证据报告、QA 记录、日志或文档，其版本口径是否与提交时点一致：HEAD、分支、工作区状态、“修复已提交/未提交”等声明在提交后是否仍成立。同一提交内的报告通常描述提交前状态；不成立时按“文档时点”降级为建议或“待确认”，不据此否定代码结论；若报告是唯一验证证据，降低结论置信度。
- 是否有 WIP、调试输出、临时文件、被注释掉的代码。
- 是否有 revert 后又重新引入同一问题。
- 历史中是否出现密钥、令牌、个人路径或内网地址；只报告位置与处置建议。

提交信息规范按仓库实际历史推断，不强行套 Conventional Commits。

## E 聚合与趋势

- 同一类问题是否在多个提交反复出现；出现两次以上时，考虑是流程或约定缺口，而不只是单点缺陷。
- 热点文件/目录是否集中在少数模块；是否与近期需求相关。
- 与上次审查相比：已修复、仍存在、新出现。只有拿到上次报告或基线时才能下结论。
- 测试、文档、迁移是否持续滞后于源码改动。
- 是否出现“提交越来越大、审查越来越晚”的趋势。

## 严重度

| 级别 | 含义 | 处理建议 |
| --- | --- | --- |
| P0 致命 | 数据损坏、安全漏洞、必然故障、不可回滚的契约破坏 | 优先修复，必要时回退 |
| P1 重要 | 高概率缺陷、明显事务/并发/资源问题、关键路径缺测试 | 合并前或下一批修复 |
| P2 一般 | 可维护性、局部重复、边界不清、非关键测试缺口 | 排期处理 |
| P3 建议 | 命名、注释、轻微简化、可选优化 | 视成本处理 |

没有证据的条目写“待确认”，不给严重度。

## 来源与取舍

- 固定基点、三点 diff、分轴不混排、项目约定覆盖通用基线、跳过工具已强制项：借鉴 Matt Pocock 的 `code-review`（固定版本与许可见公开仓库来源说明）。
- `BASE_SHA`/`HEAD_SHA` 范围模板、只读审查、给审查者精炼上下文：借鉴 Superpowers 的 `requesting-code-review`（固定版本与许可见公开仓库来源说明）。
- 五轴审查、严重度分级、结构性问题给出迁移方向：借鉴 Addy Osmani 的 `code-review-and-quality`（固定版本与许可见公开仓库来源说明）。
- 无 diff 即停、读完整文件、历史内容按不可信数据处理、混合关注点拆分：借鉴 ECC 的 `commit-reviewer` 与 `code-review`（固定版本与许可见公开仓库来源说明）。
- 不采用固定数值阈值、强制 Spec 轴、默认多 Agent 编排、自动修复或自动提交。
