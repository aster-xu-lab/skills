# 降级、熔断与回退

降级的目标是**保住核心可用性并让失败可见**，不是把错误藏起来。回退的目标是**恢复已知可用的旧行为**，不是修复根因。

## 触发条件

先定义什么情况触发，再定义触发后做什么：

| 信号 | 典型阈值来源 | 注意 |
| --- | --- | --- |
| 超时/首 token 超时 | 业务可接受延迟 | 区分模型慢与网络慢 |
| 错误率 | 滑动窗口 | 排除客户端取消与参数错误 |
| 限流/配额拒绝 | 供应商返回码 | 区分临时限流与硬配额 |
| 成本超预算 | 单请求/租户/全局 | 硬上限与软告警分开 |
| 依赖不可用 | 检索、工具、向量库 | 部分依赖失败可局部降级 |
| 输出不合法率 | 结构化解析失败 | 连续失败才触发，避免抖动 |

阈值来自业务可接受度与历史基线，不凭感觉。触发后要有冷却与恢复条件，避免反复抖动。

## 降级层级

按代价从小到大排列，先定义顺序再实现：

1. **重试/换端点**：只对瞬时且幂等的失败；避免多层叠加重试。
2. **小模型/备用模型**：质量下降可接受时使用；要有评测对照。
3. **规则/模板兜底**：确定性强、可解释；明确哪些字段由规则填充。
4. **缓存旧结果**：标注数据时间，不用过期结果冒充当前结论。
5. **人工队列**：异步处理，告知用户预计延迟。
6. **明确失败**：返回可识别错误与重试建议，不返回空结果。

每一级都要回答：用户看到什么、哪些功能不可用、如何恢复、谁被通知。

## 开关与灰度

1. 降级开关按功能/租户/模型维度可独立控制，不只一个全局开关。
2. 开关变更要留痕：谁改、何时、原因、影响范围。
3. 新降级策略先灰度到小流量，观察错误率、延迟、成本和用户反馈。
4. 开关默认值要安全：配置缺失时不应放大风险。

## 可观测

降级必须可观测，至少记录：

- 触发原因与阈值。
- 降级层级与影响的功能/租户。
- 降级持续时间与恢复时间。
- 降级期间的用户结果（成功、部分成功、失败）。
- 成本变化，避免降级后成本未降反升。

只记录“发生降级”不够，无法判断影响和恢复。

## 回退

1. 提示、模型、检索索引、工具配置、参数都要版本化，能定位当前生效版本。
2. 回退要能一键恢复到已知基线，并验证回退后的行为与指标。
3. 回退不等于修复：根因仍在时，回退只是争取时间；要另起修复任务。
4. 数据与契约兼容：回退不能假设数据库、缓存或消息格式可降级；迁移要向前兼容。
5. 回退后重跑关键评测与冒烟路径，不能只看服务启动成功。

## 演练

1. 至少演练一次：模型超时、限流、预算超限、检索为空、输出不合法。
2. 演练记录实际触发路径、恢复时间和用户影响，不只看开关能否打开。
3. 演练发现的问题回到评测集与告警规则，不留在口头。

## 反模式

- 降级返回空列表或默认值，调用方无法区分“没有结果”和“失败”。
- 只加超时不做降级，超时后请求堆积。
- 降级开关没有恢复条件，长期停留在降级态。
- 回退后不验证，认为“回到旧版本就没事”。
- 多层重试叠加，放大故障与成本。
- 把降级率写成 0 当作健康，实际从未触发过。
