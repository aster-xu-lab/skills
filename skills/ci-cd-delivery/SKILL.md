# CI/CD 交付流水线

先探测项目真实的构建工具、测试命令、制品形态、环境与发布入口，再谈流水线。不要默认项目使用 GitHub Actions、Jenkins、Docker 或某种分支模型。

本 Skill 管“变更如何被验证、制品如何晋级、发布如何可回滚”。具体流水线语法、云平台与桌面打包细节由目标项目或对应 Skill 负责。

## 适用与不适用

适用：

- 新建或改造 CI 质量门禁、测试分层与构建流程。
- 制品版本、不可变性、环境晋级与发布策略。
- 灰度、金丝雀、蓝绿、特性开关与回滚设计。
- 发布前检查、发布证据矩阵与失败分级。
- 审查“CI 绿了但线上出问题”的流程缺口。

不适用：

- 只跑一次本地构建、编译或单测。
- 云平台 IaC、集群运维、监控平台搭建（按目标项目能力处理）。
- 桌面签名、公证、安装包与自动更新细节（走 `desktop-release`）。
- 具体 CI 厂商的 YAML 写法；本 Skill 给门禁与证据结构，语法以目标项目为准。

## 硬规则

1. **门禁自动化且不可跳过**：测试、静态检查、类型检查、构建至少有一道自动门禁；失败时修问题，不跳过规则。（来源：shift-left 与质量门禁实践）
2. **一次构建，多环境晋级**：同一制品从测试到生产，不为不同环境重新构建。（来源：制品不可变与晋级原则）
3. **配置与密钥不入制品**：环境差异通过配置注入；构建日志与产物不暴露凭据。（来源：本库安全边界）
4. **迁移向前兼容**：数据库与消息格式变更要能被旧版本读取；回滚不假设可以降级数据库。（来源：发布兼容与回滚边界）
5. **发布可观测、可回滚、可灰度**：每次发布有成功判据、监控项和回退方式；回滚不等于修复。（来源：`desktop-release` 与本库交付证据原则）
6. **证据分级**：构建成功 ≠ 部署成功 ≠ 安装成功 ≠ 流量验证成功；分别记录状态。（来源：本库证据分级）
7. **不把 CI 绿当生产验证**：静态检查与单测通过不证明真实依赖、数据与流量下正确。（来源：验证边界）
8. **项目工具链优先**：分支模型、制品库、部署方式以项目约定为准，不强行套用某家实践。（来源：本库“技术栈随项目”原则）

## 工作流

### 步骤 0：探测真实交付链

1. 读项目约定、构建文件、CI 配置、制品库、环境清单与发布文档。
2. 确认：语言与版本、构建命令、测试分层、制品形态（jar/镜像/桌面包）、目标环境、发布入口与审批。
3. 记录当前门禁、失败处理、缓存与并行策略；没有 CI 时说明从哪一步开始最小闭环。

### 步骤 1：设计质量门禁

读取 `references/pipeline-gates.md`。按成本从低到高排：

静态检查 → 类型/编译 → 单元测试 → 集成/契约测试 → 构建 → 安全与依赖检查 → 端到端（可选）。

每道门禁定义：触发条件、超时、失败是否阻断、重跑策略、flaky 处理。门禁数量不是目标，**能稳定捕获真实缺陷**才是。

### 步骤 2：构建与制品

读取 `references/artifacts-and-promotion.md`。确认：

- 制品版本来自哪里，是否唯一、可追溯。
- 构建是否可复现：依赖锁定、构建缓存、环境变量。
- 制品是否不可变，是否带哈希/签名。
- 配置与密钥如何注入，是否与制品分离。

### 步骤 3：环境晋级

测试 → 预发 → 生产的每一跳定义：谁能触发、需要什么证据、失败如何停、如何回退。晋级不是复制文件，是**同一制品 + 不同配置**。

### 步骤 4：发布策略与回滚

读取 `references/release-and-rollback.md`。选择与风险匹配的策略：

- 一次性发布、滚动、蓝绿、金丝雀、特性开关。
- 成功判据（错误率、延迟、业务指标）与观察窗口。
- 回滚触发条件、回滚步骤、回滚后的验证。
- 数据库迁移与消息兼容的前滚/回退限制。

### 步骤 5：发布证据与交付

输出：变更范围、门禁结果、制品版本与哈希、各环境状态、发布策略、观察指标、回滚方式、未验证项。区分“已构建”“已部署”“已验证”。

Java/Spring 与桌面的差异读取 `references/java-and-desktop.md`。

## 不做什么

- 不替目标项目选 CI 厂商、云平台或部署工具。
- 不为通过门禁修改测试、降低断言或跳过检查。
- 不把构建成功写成发布成功。
- 不执行生产发布、上传制品或切换流量；这些按当前任务授权处理。
- 不重复 `desktop-release` 的签名、安装与更新验证细节。
