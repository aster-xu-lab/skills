# 制品、版本与环境晋级

核心原则：**一次构建，多环境晋级；制品不可变；配置与制品分离。**

## 制品是什么

先明确制品形态：jar/war、容器镜像、桌面包、静态资源包、迁移包。不同形态的版本、签名与晋级方式不同，但原则一致。

制品要能回答：

- 它由哪个提交、哪次构建产生。
- 它包含哪些依赖与资源。
- 它是否可复现、是否被修改过。
- 它要部署到哪个环境、用什么配置。

## 版本来源

1. 版本来自单一真值：构建元数据、标签或发布配置，不从目录名或提交说明推断。
2. 语义版本或项目约定要一致；预发布、构建号、渠道标识不混用。
3. 同一版本不重复发布不同内容；需要重发时递增版本或构建号。
4. 版本与制品哈希一起记录，便于回溯。

## 可复现构建

1. 锁定依赖版本与锁文件；构建时使用锁定结果，不解析浮动版本。
2. 固定构建环境（JDK/Node/基础镜像版本），记录工具链版本。
3. 构建脚本不依赖本机未提交文件；工作区脏时说明差异。
4. 构建产物中的时间戳、路径与随机值尽量可控；不能完全复现时记录差异。

## 不可变与完整性

1. 制品发布后不覆盖；修复走新版本。
2. 制品带哈希或签名；晋级时校验，不信任传输过程。
3. 制品库保留策略与回滚窗口匹配；旧制品删除前确认没有回退需求。
4. 不从制品包中暴露凭据、调试文件或内部路径。

## 配置与密钥

1. 环境差异通过配置注入：环境变量、配置中心、挂载文件；不重新构建。
2. 密钥不进入制品、镜像层、构建日志或缓存。
3. 配置变更有版本与审计；谁能改生产配置要明确。
4. 配置缺失时默认安全：不放大权限、不绕过鉴权、不降级到不安全模式。

## 环境晋级

每一跳定义：

| 项目 | 要求 |
| --- | --- |
| 触发者 | 谁能发起晋级 |
| 前置证据 | 门禁结果、测试报告、审批 |
| 配置 | 目标环境配置是否就绪 |
| 失败处理 | 失败停在哪、如何回退 |
| 观察窗口 | 晋级后观察多久、看什么指标 |

晋级是**同一制品 + 不同配置**，不是重新构建。需要重新构建时，说明原因并重新走门禁。

## 制品库与保留

1. 制品库按环境/渠道隔离权限。
2. 保留至少覆盖回滚窗口与审计要求。
3. 删除制品前确认没有环境仍引用。
4. 制品元数据（提交、构建号、哈希、签名、扫描结果）与制品一起保留。

## 反模式

- 每个环境重新构建，导致“测试过的不是上线的”。
- 用目录名、分支名或提交说明推断版本。
- 制品覆盖发布，旧哈希失效。
- 密钥写进镜像层或构建参数。
- 晋级只复制文件，不校验哈希与配置。
- 制品库无保留策略，回滚时找不到旧版本。

（来源：制品不可变与一次构建多环境晋级的通用实践；本库配置与密钥边界）
