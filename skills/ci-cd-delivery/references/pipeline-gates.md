# 质量门禁与流水线结构

本文件只写门禁设计判据，不绑定 CI 厂商。具体语法按目标项目现有配置。

## 门禁顺序

按“发现成本从低到高”排列，越早失败越便宜：

```
静态检查 → 编译/类型检查 → 单元测试 → 集成/契约测试 → 构建 → 安全与依赖检查 → 端到端（可选）
```

- **静态检查**：格式、lint、静态分析。秒级，先跑。
- **编译/类型检查**：语言与框架约束；Java 项目至少 `compile` 或等价目标。
- **单元测试**：快、稳定、无外部依赖；失败应能定位到单一逻辑。
- **集成/契约测试**：数据库、消息、外部接口；按风险选择，不是每个 PR 都跑全量。
- **构建**：产出可部署制品；构建失败不应进入后续阶段。
- **安全与依赖检查**：漏洞扫描、密钥扫描、许可证策略；按项目要求阻断或告警。
- **端到端**：覆盖关键用户路径；成本高，按发布节奏或夜间运行。

门禁数量不是目标。**能稳定捕获真实缺陷、且维护成本可接受**才是。

## 测试分层选择

| 层 | 覆盖 | 运行时机 |
| --- | --- | --- |
| 单元 | 纯逻辑、边界、异常 | 每个 PR |
| 切片 | Controller、Repository、消息监听 | 每个 PR 或按模块 |
| 集成 | 真实数据库/中间件/契约 | PR 或合并前 |
| 端到端 | 关键用户路径 | 合并前、发布前、夜间 |

不要在 PR 门禁里塞全部端到端；也不要只跑单元测试就宣称覆盖集成风险。

## 触发与范围

1. PR：快速门禁，覆盖变更相关模块与公共契约。
2. 合并到主线：完整门禁 + 构建制品。
3. 定时：全量测试、依赖更新、安全扫描、端到端。
4. 发布：制品晋级 + 发布前检查，不重新跑全量除非项目要求。

按变更路径选择测试范围时，公共模块、配置、构建文件和依赖变更要触发更宽范围。

## 失败处理

- **阻断门禁失败**：修问题，不跳过规则、不降低断言、不删除测试。
- **flaky 测试**：先隔离并记录，限期修复；不能长期用重跑掩盖。
- **环境失败**：区分代码失败与基础设施失败；环境问题要修复或标记，不伪装成通过。
- **超时**：设置合理超时；超时视为失败，不无限等待。
- **重跑**：只对确认的瞬时失败重跑；重跑次数与结果要记录。

## 缓存与并行

1. 依赖缓存要带锁文件哈希；缓存键变化时失效。
2. 构建缓存不能跨不可信来源共享；PR 与主线的缓存权限分开。
3. 并行任务要避免共享可变资源；数据库测试用独立 schema/容器。
4. 缓存命中率是优化项，不是正确性保证；缓存损坏要能自动回退。

## 分支保护与审批

1. 主线至少要求：门禁通过、评审通过、无未解决冲突。
2. 紧急通道要有记录与事后补验证，不能成为常态。
3. 谁能合并、谁能跳过门禁、跳过记录在哪里，要明确。
4. 不把“管理员可以直接推”当作流程不存在。

## 密钥与权限

1. CI 密钥按环境隔离，最小权限；不在日志、制品或缓存中暴露。
2. PR 来自 fork 时，默认不授予生产密钥。
3. 密钥轮换与吊销路径要存在；泄露时能快速失效。
4. 构建脚本不执行来源不明的代码或下载未锁定依赖。

## 反模式

- 门禁失败后直接跳过或注释测试。
- 只跑单元测试，集成风险留给生产。
- flaky 测试长期重跑，没人修。
- 所有测试每次全量跑，反馈慢到没人看。
- PR 与主线共用生产密钥。
- 把 CI 绿灯当作发布批准。
- 门禁数量很多，但没有一条能捕获真实历史缺陷。
