# 发布策略、观察与回滚

发布的目标不是“部署成功”，而是**在可观测、可回滚的前提下让变更安全到达流量**。

## 策略选择

| 策略 | 适合 | 代价 |
| --- | --- | --- |
| 一次性发布 | 低风险、可快速回滚、内部系统 | 爆炸半径大 |
| 滚动发布 | 无状态服务、实例可替换 | 新旧版本短暂共存 |
| 蓝绿 | 需要快速切换与完整回退 | 双倍资源、数据兼容要求高 |
| 金丝雀 | 高风险变更、需要真实流量验证 | 需要流量切分与指标对比 |
| 特性开关 | 部署与发布解耦、灰度与实验 | 开关治理成本、死代码清理 |

策略与风险匹配；不为了“先进”选择项目没有能力运维的方案。

## 成功判据与观察窗口

发布前定义：

- 技术指标：错误率、延迟 P95/P99、饱和度、依赖错误。
- 业务指标：关键转化、订单/请求成功率、人工介入量。
- 观察窗口：多久算稳定；窗口内出现什么立即回滚。
- 对比基线：发布前同一时段的指标。

没有成功判据的发布无法判断是否成功。

## 回滚

1. **触发条件**：错误率、延迟、业务指标、依赖失败、用户反馈达到阈值。
2. **回滚步骤**：切回旧制品/旧配置/旧开关，按预演步骤执行。
3. **回滚验证**：回滚后重跑关键指标与冒烟路径，不只看服务启动。
4. **数据兼容**：数据库迁移、消息格式、缓存结构必须向前兼容；回滚不假设可以降级数据库。
5. **回滚不等于修复**：根因仍在时，回滚只是止损；另起修复任务。
6. **回滚记录**：时间、原因、影响范围、恢复时间、后续动作。

## 数据库与消息兼容

1. 迁移分 expand → migrate → contract，跨多次发布完成。
2. 新字段先可空/带默认值，旧版本可继续写入。
3. 删除字段或收紧约束前，确认所有读写方已升级。
4. 消息格式变更要能被旧消费者忽略或兼容；不假设所有消费者同时升级。
5. 回滚窗口内保留旧版本可读的数据结构。

## 前滚

当回滚成本高于前滚时，定义前滚路径：修复版本、数据修复脚本、补偿任务。前滚同样要有验证与观察窗口，不因为“向前”就跳过证据。

## 发布证据矩阵

| 阶段 | 证据 |
| --- | --- |
| 构建 | 制品版本、哈希、依赖锁定、构建日志 |
| 门禁 | 测试/静态检查/安全扫描结果 |
| 部署 | 目标环境、配置版本、部署时间、实例状态 |
| 启动 | 健康检查、关键依赖连通性 |
| 流量 | 错误率、延迟、业务指标、告警 |
| 回滚 | 触发原因、步骤、恢复时间、验证结果 |

每个阶段分别记录状态；前一阶段成功不证明后一阶段成功。

## 反模式

- 发布没有成功判据，只看“部署完成”。
- 回滚步骤从未演练，真出事时找不到旧制品。
- 数据库迁移不可逆，却假设可以回滚应用。
- 新旧版本共存期契约不兼容。
- 金丝雀只看技术指标，不看业务指标。
- 回滚后不验证，认为“切回去就好了”。
- 把发布审批当成风险控制的全部。
