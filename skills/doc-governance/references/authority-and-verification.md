# 权威地图与验证方法

解决两个问题：同一份事实该由谁维护；改完之后能验证到什么程度。

## 一、权威边界

阅读顺序不等于权威顺序。读者先看哪份材料，和哪份材料对某个事实有最终决定权，是两件事。

先产出再动手：

| 文件 | 维护什么 | 不重复维护什么 |
| --- | --- | --- |
| `README.md` | 项目介绍、启动、常用入口 | 历史跑次、完整 SOP、能力清单 |
| 当前状态文档 | 现有能力、验证范围、未决差异 | 按时间追加的修复日志、完整接口说明 |
| `AGENTS.md` | 工具无关的硬约束、必要命令、领域路由 | 全量 Skill 清单、历史验收报告 |
| 规则目录 | 共享约束与易错边界 | 宿主入口副本 |
| 领域文档 | 可直接使用的契约、SOP、数据模型 | 宿主特有的调用方法 |
| 有日期的评审、QA、bench | 当时版本、样本、环境与证据 | 当前承诺或未结缺陷台账 |
| 宿主要求文件（`CLAUDE.md` 等） | 该宿主的加载方式 | 再写一份 `AGENTS.md` |

模板来源：工程仓库文档治理约定。项目没有这张表时，按实际文件重新填，不照抄示例行。

### 冲突裁决顺序

1. 先判断冲突是「要求」还是「实际实现」。
2. 实现以代码、构建脚本与配置为准。
3. 要求以用户指示和根约定文件为准。
4. 日期更晚的文档不自动覆盖用户的明确决定。
5. 两者确实不符时，在状态文档记录差异并单独处理，不改措辞声称一致。

来源：工程仓库文档治理约定。

## 二、验证方法

改完后按下表检查，并说明哪些做了、哪些没做。

| 检查 | 做法 | 能证明什么 |
| --- | --- | --- |
| 相对链接 | 抽取所有本地链接目标，确认存在且不越出仓库 | 不会出现死链或跨仓依赖 |
| 命令引用 | 文档里的脚本命令与 `package.json`、`Makefile` 或 CI 配置逐条比对 | 文档没有写过时命令 |
| frontmatter | 解析 Skill、Agent 等文件的 YAML 键与目录名、名称 | 结构合法 |
| 编号一致 | 标题声明的条数与实际条目数比对 | 精简后没有残留计数 |
| 交叉引用 | 引用的章节号、锚点在目标文件中仍存在 | 指针没有指向已删内容 |
| 生成文件 | 确认生成器、源文件与生成命令；未重新生成时写明残余风险 | 生成物与源一致 |

以上都是结构检查。它们**不能**证明：宿主的自动路由、生成物在运行时被正确加载、文档描述的行为在真实环境中成立。报告时分开写。

来源：工程仓库文档治理约定的验证要求。

## 三、历史证据处理

- 保留原始正文与路径，不为了整洁重写。
- 顶部标注历史属性：报告日期、适用版本、环境与当时范围。
- 当前入口指向历史证据，但不复制其结论。
- 旧报告里的未结项不等于今天仍未完成；使用前核对代码与最新证据。
- 移动或删除前检索所有引用；仍有活跃用途的先合并再删。

来源：工程仓库文档治理约定的历史证据处理要求。

## 四、执行记录

如果项目已有执行记录（如带日期的治理记录表），在其后追加：时间、动作、结果。
没有时不要凭空新建一套治理体系；在收尾报告里说明未建立，并给出是否值得建立的判断。
